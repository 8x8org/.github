# MSG238 — Public Growth and Community Activation 0.0.1

Product: **8x8 OS 0.0.1 Beta**

## Purpose

Turn the current quiet GitHub organization into an active, truthful public program without exposing the private 8x8 control plane or inventing adoption.

## Current observed problems

- the organization profile is documentation-heavy and visually weak;
- the only GitHub Project is private and contains no items;
- Discussions contains only the default welcome announcement;
- public repositories have little social proof, few visible contributors, and weak newcomer pathways;
- no sustained release, announcement, tutorial, showcase, or contributor campaign exists;
- organization description still says `Human-AI Controlled Web3 Operating System`, which no longer matches the broader 8x8 identity;
- public work is split across issues, pull requests, MSG packets, receipts, and local runtime evidence instead of one public roadmap.

## Public activation workstreams

### 1. Organization identity

- update the organization description to `Evidence-governed operating system for human and AI organizations`;
- use one coherent logo, hero image, social preview, typography, and 0.0.1 Beta identity;
- publish a product-family map covering User Edition, Protocol, Studio, Academy, Truth Console, testnet research, and Future Lab;
- retain explicit PRIVATE_PAST, PUBLIC_PRESENT, FUTURE_LAB, and PROTECTED_BETA boundaries.

### 2. GitHub Project activation

Create or repair one public project with these initial views:

- Public Roadmap;
- In Progress;
- Protected Beta;
- Contributor Ready;
- Security and Accessibility;
- Research and Future Lab;
- Blocked Owner Gates;
- Released 0.0.1 Units.

Required fields:

- Status;
- Lane;
- Reality;
- Evidence State;
- Priority;
- Owner;
- Release Unit;
- Risk;
- Updated At.

Seed the project with current public-safe issues and pull requests. Configure automatic addition for selected repositories and close/archive rules for completed work.

### 3. Discussions program

Publish and maintain:

- Start Here and Introductions;
- 8x8 OS 0.0.1 Beta announcement;
- weekly build log;
- public roadmap and voting thread;
- contributor help and good-first-task thread;
- architecture questions;
- Studio and design showcase;
- protocol and SDK proposals;
- security and privacy FAQ;
- monthly community demo thread.

Never publish private topology, credentials, runtime logs, precise locations, wallet material, or unverified deployment claims.

### 4. Contributor pipeline

- create labeled `good first issue`, `help wanted`, `documentation`, `accessibility`, `design`, `security`, and `testing` tasks;
- publish local setup and first-contribution guides;
- add issue and pull-request templates;
- create a contributor recognition page based on merged, evidenced work;
- provide small deterministic tasks with acceptance tests;
- add office-hours or asynchronous review cadence;
- maintain a public contributor scoreboard based on verified contributions, not promises.

### 5. Promotion and distribution

Prepare truthful reusable launch assets:

- 30-second product explanation;
- one-minute demo script;
- launch post;
- GitHub announcement;
- LinkedIn post;
- Reddit and Hacker News submissions where appropriate;
- developer community outreach;
- contributor invitation;
- architecture diagram;
- screenshots and short demo clips;
- public changelog and release notes;
- media kit with approved logos and social previews.

No paid advertising or financial commitment should occur without exact owner authorization and a declared budget.

### 6. Release movement

Establish a predictable rhythm:

- weekly public build note;
- biweekly contributor task refresh;
- monthly 0.0.1 Beta demonstration;
- release notes for every promoted public-safe unit;
- visible rollback and known-limitations notes;
- stale-project and unanswered-discussion review.

## Acceptance criteria

- organization description matches the evidence-governed identity;
- public profile has a strong hero, clear calls to action, and product map;
- a public project contains real issues and pull requests;
- at least five purposeful discussion threads exist;
- at least ten bounded contributor-ready tasks exist;
- every public repository has a social preview, coherent README, topics, security policy, contribution guide, and release status;
- public announcement assets are created and approved;
- no private or unsupported claims are exposed;
- activity is measured by verified issues, pull requests, discussions, releases, contributors, and public-safe deployments, not decorative counters.

## Current truth

This document defines the activation program. It does not prove that the GitHub Project has been populated, discussions have been published, advertisements have run, or contributors have joined.
