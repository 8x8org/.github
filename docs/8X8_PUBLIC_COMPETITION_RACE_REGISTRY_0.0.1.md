## Status vocabulary

- `SUBMITTED_FROZEN_AWAITING_RESULT` — external submission exists and current organizer guidance requires preservation while the result is unresolved.
- `ACTIVE_BUILD_NOT_SUBMITTED` — active eligible work exists but no final submission receipt exists.
- `WATCHLIST_NOT_ENTERED` — a verified current race is relevant but no 8x8 registration/submission is claimed.
- `RESULT_UNVERIFIED` — a scheduled result boundary has passed or is near, but no authoritative outcome receipt has been recorded.
- `PROJECT_ATTACHED_PRESENT_PROVEN` — issue attachment to the public GitHub Project has been independently observed/receipted.
- `PROJECT_ATTACHMENT_PENDING` — issue exists but Project-v2 attachment is not yet proven.

## OpenAI Build Week boundary

The Build Week submission has a previously established freeze boundary. Until an authoritative result is independently recorded, the submitted material remains preserved. A scheduled winner time is not itself a winner receipt. The public registry and unrelated repositories may continue to evolve because they do not mutate the frozen submission.

## Benchmark and ranking are separate from competitions

Issue #24 governs scores, rates, rankings and leaderboards. A historical internal scorecard is not an official competition result and a competition result is not automatically a system benchmark.

Ranking progression:

`UNMEASURED → BASELINED → REPRODUCED → COMPARABLE → EXTERNALLY_VERIFIED → RANKED`

`TOP_1`, `BEST`, `100/100` and any numeric rank require an explicit benchmark/version, frozen denominator, exact source/runtime/model/provider/configuration, comparable reference results, timestamp/environment, raw reproducible receipt, freshness/invalidation policy, and an independent authoritative result where the rank is external.

## Fair-race policy

1. Never claim `SUBMITTED`, `FINALIST`, `WINNER`, `DEPLOYED`, user counts, revenue, benchmark leadership, uptime, production calls or judge access without the corresponding receipt.
2. Preserve organizer-required frozen submissions exactly.
3. Separate pre-existing One-Fabric work from competition-window work whenever eligibility requires it.
4. Publish public-safe status, official rules/deadlines, provenance, blockers and results; keep credentials, PII, private topology and privileged runtime evidence private.
5. Competition constraints remain bounded adapters/projections, not One-Fabric constitutional law.
6. Useful competition work should converge back into reusable capabilities after the event.
7. Missing a deadline is preferable to corrupting eligibility, security or evidence integrity.
8. `fabric://8x8/core` remains canonical.
9. Agents may maintain the registry and prepare work, but an irreversible or high-impact external action still requires its authority gate.
